# Dokumentasi Debugging — Unit Kompetensi J.620100.025.02

Dokumen ini menjadi bukti tertulis pelaksanaan proses **debugging sistematis** (*Melakukan Debugging* — Kode Unit `J.620100.025.02`) selama pengembangan dan audit kualitas **Garage Rental Management System**.

---

## 1. Metodologi & Perangkat Debugging

Proses identifikasi, isolasi, perbaikan, dan verifikasi kesalahan dilakukan dengan pendekatan terstruktur:

1. **Reproduksi Terisolasi**: Menggunakan database SQLite `:memory:` dan fungsi `clock` terinjeksi (*fixed clock*) pada Vitest & Supertest agar bug terkait tanggal (tahun kabisat, peralihan bulan/tahun, batas waktu `Asia/Jakarta`) dapat direproduksi secara deterministik.
2. **Inspeksi Stack Trace & Error Terstruktur**: Seluruh error operasional diarahkan ke [errorHandler.js](file:///c:/Users/zeusd/Documents/GitHub/MKR/src/middleware/errorHandler.js) dengan pemetaan hierarki kelas [errors.js](file:///c:/Users/zeusd/Documents/GitHub/MKR/src/utils/errors.js) (`ValidationError` 400, `AuthenticationError` 401, `ForbiddenError` 403, `NotFoundError` 404, `ConflictError` 409) serta logging `[ServerError]` untuk error tak terduga (500).
3. **Profiling Query SQLite**: Memanfaatkan `EXPLAIN QUERY PLAN` untuk memverifikasi penggunaan index B-tree pada query agregasi laporan.
4. **Audit Keamanan & Code Coverage**: Menggunakan `@vitest/coverage-v8` (`npm run test:coverage`) serta skrip audit JSDoc dan pengujian DOM (`jsdom`) untuk mendeteksi cabang kode yang belum teruji.

## 2. Log Temuan Bug, Analisis Akar Masalah, & Perbaikan

| No | Kategori | Gejala / Temuan | Akar Masalah (Root Cause) | Perbaikan yang Diterapkan | Bukti Verifikasi |
|---:|---|---|---|---|---|
| 1 | Testing / Module System | `npm test` gagal dengan `Error: Vitest cannot be imported in a CommonJS module using require()` | Vitest v3 hanya mendukung ESM `import` untuk modul `vitest`, sementara file uji sebelumnya memakai `require('vitest')`. | Mengganti import runner Vitest menjadi `import { describe, it, expect } from 'vitest'` pada seluruh file test. | `npm test` lulus 100%. |
| 2 | Database Schema | Ketidakselarasan jumlah tabel (7 tabel pada implementasi awal vs 8 tabel pada ERD sertifikasi). | Tabel master `garage_types` belum dipisahkan dan nama kolom belum diselaraskan dengan ERD. | Menambahkan tabel `garage_types`, entitas OOP `GarageTypeConfig`, serta menyelaraskan seluruh nama tabel dan kolom (`admin`, `tenants.is_verified`, `rentals.total_price`, `rental_extensions.rentalext_id`, dll.) di `schema.js`, seluruh repository, frontend, dan `erd.puml`. | `api.test.js` memverifikasi tepat 8 tabel pada `sqlite_master`. |
| 3 | Performa Database (N+1 Query) | `RentalRepository` memanggil `getExtensionsForRental()` di dalam `.map()` dan `ReportRepository.getTenantReport()` menjalankan query distinct garasi di dalam loop penyewa. | Pengambilan relasi anak dilakukan per baris secara berulang (*N+1 query*). | Menambahkan batch loader `getExtensionsMapForRentals(rentalIds)` (`WHERE rental_id IN (...)`) pada `RentalRepository.js` serta mengganti loop query di `ReportRepository.js` dengan satu query agregasi `COUNT(DISTINCT r.garage_id)`. | `securityAndPerformance.test.js` & `api.test.js` #19. |
| 4 | Performa Database (Non-SARGable) | Filter tanggal laporan menggunakan `WHERE substr(start_date, 1, 4) = ?` dan `substr(created_at, 1, 7) = ?`. | Pembungkusan kolom terindeks di dalam fungsi `substr()` membuat SQLite melakukan full table scan dan mengabaikan index B-tree. | Mengganti seluruh predikat filter tanggal dengan rentang setengah terbuka SARGable `>= start AND < endExclusive` melalui `getYearRangeBounds()` dan `getMonthRangeBounds()`. | Tes `EXPLAIN QUERY PLAN` di `api.test.js` membuktikan `USING INDEX idx_rentals_dates` dan `USING INDEX idx_extensions_created_at`. |
